# Demo 制作工具架构与开发计划

日期：2026-09-19。目标：在现有 Unity 工程内逐步形成可复用的 Demo 制作工具。本文是设计与任务计划，不代表工具已经实现；本轮不开发功能。

## 1. 工具最终应支持的工作方式

希望以后制作一个新 Demo 时，主要在 Unity 场景和 Inspector 中完成以下工作：

1. 从模板创建新场景，获得地面、边界、镜头、出生点和运行入口。
2. 选择 Player 配置，设置人数、默认主控、基础属性和这个场景可用的能力。
3. 把交互物 Prefab 放进场景，或者给普通模型挂交互组件；配置动作、条件、持续时间、协作方式和反馈。
4. 给交互物绑定局部 Scene UI；根据 Demo 需要选配主 HUD，不强制显示统一的大面板。
5. 点击运行，由场景入口自动生成或接管 Player，并完成输入、镜头、交互物和 UI 的绑定。
6. 新玩法超出现有行为库时，只增加一种行为或能力脚本及其配置，不修改所有 Player、全局枚举和总控制器。

工具的产出应是“可运行的场景模板 + 可挂载组件 + 可组合 Prefab + 简单编辑辅助”，而非先做一个庞大的通用游戏框架。已有行为可以通过配置组合；全新的规则仍可能需要写一个小脚本，不能承诺所有玩法都靠勾选实现。

### 2.1 现有资产如何处理

| 当前实现 | 可以利用的部分 | 不能直接作为通用工具的原因 |
|---|---|---|
| `ActorView` | 接收外部指令的移动、碰撞处理、表现锚点 | 绑定三角色身份色、选中表现与出生点缓存；不是完整通用 Player |
| `FixedAngleCamera` | 固定角度、目标切换和平滑跟随 | 应作为可选镜头方案；新工具不强迫所有 Demo 使用相同视角 |
| `DemoRuntime` | 唯一输入、共享时钟、主控角色路由的组织思路 | 直接认识庆典 HUD、会话、三角色和奖杯规则 |
| `DemoSession` | 庆典规则、工位批次、效果和回顾的现有实现 | 固定三个角色及庆典目标枚举，应保留为庆典业务模块 |
| `TargetView`、`DemoHud` | 各种可视反馈的样例 | 读取整个庆典状态，无法只换配置变成通用组件 |
| 旧 `InteractionAction`、`Interactable` | 在物体上挂行为、显式组合的作者工作方式 | 同步动作链无中间状态回滚，默认变色行为隐含；不具备共享计时和能力边界 |
| 旧 `PlayerInteractor`、`PlayerController` | 单角色原型代码参考 | 各 Player 自读输入，直接复制会同时响应；共享 InputAction 生命周期也需要重新设计 |

旧交互上下文依赖具体 `PlayerInteractor`；新的行为契约不继续绑定这一旧控制器。旧动作若要利用，通过小适配器迁移，并明确失败行为，不能把整套旧输入和新输入同时挂进场景。

当前代码核对来源为 `Assets/CelebrationDemo` 与 `Assets/_Project/Scripts`，基线见第一份文档。下文所有组件名称均为拟议名称，可在实际开发时简化。

### 2.2 第一版范围

第一版应具备：自动放入 Player、唯一输入入口、放置交互物、即时行为、计时/协作行为、条件与自动动作选择、状态/外观变化、临时属性效果、对象 Scene UI、可选 HUD、场景能力覆盖及一个自定义能力示例。

真实联网、跨局存档、背包经济、任务编辑器、节点图、完整 RPG 属性系统、复杂程序化地图均不纳入第一版。本地角色切换可模拟同步协作和留下行为痕迹，但不能等同于真正的联网同步或离线异步服务。

## 3. 总体结构与依赖

运行结构分为五部分：

| 部分 | 职责 | 依赖限制 |
|---|---|---|
| 基础契约 | 角色/目标身份、交互请求、状态投影、执行结果、时钟接口 | 不认识庆典、UI、模型资源 |
| Player 与场景运行时 | 生成与管理角色、接收输入、移动、能力、场景生命周期 | 通过契约访问交互，不认识具体水果或奖杯 |
| 交互物运行时 | 目标选择、条件、行为执行、计时和协作 | 不直接调用具体 HUD；不从键盘自行读 F |
| 表现层 | 模型反馈、动画/粒子/声音、Scene UI、可选 HUD | 消费结果和状态，不成为业务状态所有者 |
| 编辑与示例 | 模板创建、Prefab 配置、引用校验、Demo 专属规则 | 编辑代码不进入运行时依赖；示例依赖工具，工具不依赖示例 |

建议在工程内形成 `DemoKit/Runtime`、`DemoKit/Editor`、`DemoKit/Prefabs`、`DemoKit/Samples` 四个归属区。Runtime 内再按 Player、Interaction、Presentation、Scene 分组。先使用普通目录与清晰依赖，达到第二场景复用后再决定是否拆为 UPM 包；不为目录结构一次性增加很多程序集。

具体业务模块可以实现行为接口，也可以把一次行为转发给自己的会话。比如庆典适配器继续让 `DemoSession` 决定称号、发奖与历史，通用交互运行时只负责调用与反馈。不得在通用工具与业务会话中各保存一份权威进度，再靠每帧同步维持一致。

## 4. 交互物是工具的核心

### 4.1 一个交互物的组成

| 配置/组件 | 配置内容 | 运行时职责 |
|---|---|---|
| `Interactable` | 场景内稳定 ID、范围、焦点锚点、候选动作 | 注册目标、提供当前动作，不实现每种玩法的大分支 |
| `InteractionCondition` | 能力/标签要求、归属、对象阶段等 | 只读判断是否可见、可选、可执行及原因 |
| `InteractionBehaviour` | 即时或持续行为、参数、重复策略 | 创建或加入执行实例，提交该行为的实际结果 |
| 对象状态组件或业务适配器 | 开关状态、样式索引，或外部会话的绑定 | 持有这一对象真正的逻辑状态；两种所有权方式选一种 |
| `FeedbackPresenter` | 模型、材质、音效、动画、粒子等显式引用 | 根据开始/进度/完成/失败等结果表现 |
| `SceneUIBinding` | 数据源、锚点、UI Prefab、显示条件 | 展示提示、进度和局部反馈，不执行第二份业务 |

行为与反馈不混在同一个动作数组中。例如“维修后灯亮”中，维修完成和灯的开启状态是逻辑；声音、亮起动画是表现。即使关闭声音与动画，灯仍处于开启状态，晚加载的灯光视图能从状态恢复。

### 4.2 最小执行契约

- `InteractionContext`：当前场景运行实例、ActorId、TargetId、所选 ActionId，以及显式提供的能力/状态访问接口。世界坐标等 Unity 数据留在适配层，不向纯规则层传整套 PlayerController 或 HUD。
- `InteractionOffer`：稳定动作标识、显示文字或文案键、可执行状态及原因。它是查询结果，没有副作用。
- `InteractionRequest`：谁在什么对象上请求哪个动作。执行前重新验证，避免提示显示后能力到期或目标被删除。
- `InteractionRun`：持续行为的运行实例，有 RunId、拥有者、参与者、进度及生命周期。即时行为可以直接返回完成结果，无需为它建立复杂调度器。
- `InteractionResult`：业务是否完成、结构化变化及反馈信息。把“生成进度”“提交结果”与“弹出某个界面”分开。

用户通常只需要配置组件。契约只在确实新增行为时由代码作者接触；不要把内部 ID、服务名称和类名强行显示给 Demo 的玩家。

### 4.3 一次 F 的流程

1. 唯一输入入口向当前主控角色发出交互请求。
2. 目标查询在本场景注册表中选出一个目标；同一对象的多个 Collider 去重，距离接近时保持选择稳定。
3. 目标按条件和优先级给出一个动作。第一版默认一个主动作；以后确有需求再增加菜单选择。
4. 执行器重新校验并开始/加入行为；修改状态后产生结果和事件。
5. 绑定此对象的 Scene UI 和表现组件得到变化；场景需要日志时，再由日志接收器记录。

目标的“可见”“可成为候选”“可执行”需区分：有的对象应隐藏，有的应显示不能交互的原因。不能把所有不满足条件的对象都从候选中消失，也不能让距离排序器认识筷子、奖杯等业务名词。

### 4.4 即时、持续和协作行为

| 类型 | 状态所有者 | 最小策略 | 示例 |
|---|---|---|---|
| 即时 | 对象状态组件或业务会话 | 单次/可重复，完成一次提交一次 | 开灯、切换样式、提交一次行为 |
| 计时 | 对象持有的执行实例 | 单人时长、重复加入行为、完成与清理 | 维修、加工、浇灌 |
| 协作计时 | 共享对象的同一批次 | 按独立参与者数量加速、参与保留策略 | 多人一起维修或制作 |
| 业务转发 | 外部业务会话 | 明确谁负责时间、状态和记录 | 当前庆典各类行为 |

计时与协作第一版规则：

- 归一化进度按 `本段时间 × 有效参与人数 ÷ 单人所需时间` 增加。有人中途加入时，先用旧人数推进到加入时刻，再加入新成员；不能把新增人数追溯应用到已经过去的时间。
- 同一 ActorId 在同一 RunId 中只算一名参与者；共享结果每批只提交一次，参与者反馈可分别产生。
- 默认支持当前 Demo 所需的“加入后保留到完成”：离开位置、切换主控不会退出。距离持续要求、按住持续、可取消等属于不同策略，未来分别增加，不能写成全局规则。
- 行为持续不等于 Player 全局忙碌。是否占用移动或某种能力，由该行为声明；不能因一个工位在运行就禁用整个角色或其他对象。
- 对象失效、场景卸载、活动重置要明确结束运行实例并清理引用。第一版默认取消未完成实例且不发完成结果，不声称“永远不会中断”适用于卸载场景。
- 工具时钟不随 UI 打开而自动停止。每帧推进由唯一场景调度器负责；适配到已有会话的行为只能选外部会话时钟，不能两边推进。

### 4.5 条件、效果与行为组合

条件用于选择“当前能做哪个动作”，例如有某种工具标签时提供使用动作，否则提供提交动作。新条件通过组件扩展，不向全局 `TargetKind` 枚举加分支。条件检查和最终执行使用相同数据来源。

第一版组合采用“一个主行为 + 显式条件 + 多个反馈组件”。需要一次原子修改多个业务状态时，由一个主行为或业务会话完成校验与提交。不要先做多个有副作用动作串联，再把“后续失败”误报成前面的动作也没有发生。

可重复执行采用明确规则：每按一次、仅第一次、运行中加入、完成后可新开一轮。规则由配置选择，不使用“没有挂行为就默认变色”的隐含操作。未配置必要行为应在编辑校验中指出。

UnityEvent 可以作为设计人员连声音/动画的便捷表现出口；关键状态提交、协作产出和资格判断不隐藏在随意配置的回调链里。表现订阅失败不得撤销已经完成的业务或阻塞其他订阅者。

### 4.6 行为库的最小内容

第一轮不堆几十个动作，先用少量有代表性的组件覆盖复用需求：

| 行为能力 | 通用层提供什么 | 留给每个 Demo 的内容 |
|---|---|---|
| 开关/有限样式变化 | 对象状态切换和只读投影 | 哪种状态代表开门、点灯或染色 |
| 计时与协作 | 单一执行实例、进度、参与者、完成通知 | 完成后产生什么业务结果 |
| 条件选择 | 能力、标签、归属或状态的判断扩展点 | 筷子禁止捐献等具体规则 |
| 临时角色效果 | 有来源的属性修饰、期限与叠加策略 | 偷吃减速、场景加速等参数 |
| 一次事件/业务调用 | 携带身份和结果的扩展行为入口 | 购买、捐献、发奖或场景任务 |
| 表现绑定 | 指定模型/挂点的显隐、样式、动画和特效 | 资源、文案、颜色、庆典节奏 |

不把“金币 -1”文本自动当作真实扣钱，也不根据有没有一个日志面板决定是否记录业务历史。需要真实库存或长期回顾的 Demo，应显式接入自己的状态/记录模块。

## 5. Player 独立、复用与场景定制

### 5.1 Player 内部职责

| 组件/责任 | 管什么 | 不管什么 |
|---|---|---|
| `PlayerIdentity` | 运行时 ActorId、显示名、外观配置 | 固定只有 1/2/3 号、固定红黄蓝 |
| `PlayerMotor` | 接收移动命令，执行碰撞、位移、转向 | 读取键盘、庆典状态、窗口显隐 |
| `PlayerInteractor` 适配器 | 使用当前角色身份发请求、维护该角色的交互焦点 | 独立读取 F、建立第二个共享工位 |
| `PlayerCapabilities` | 已安装且被本场景启用的能力 | 通过改全局枚举实现每个新玩法 |
| `PlayerStats/Effects` | 基础属性、临时修饰、效果期限和来源 | 让其他脚本任意覆盖最终移动速度 |
| `PlayerView` | 模型、动画、选中标记和反馈锚点 | 业务奖励与活动历史 |

同一 Player 可以被人控制，也可以以后接入脚本指令源。第一版只实现键盘和可选本地角色切换；不为未来 AI 提前开发寻路。1/2/3 切换属于调试/演示控制方案，不成为 Player 本体的限制。

输入资源由场景输入服务拥有。Player 失去控制时只撤销该 Player 的输入路由，不擅自禁用所有人共用的 InputAction。移动只由一个 Motor 路径执行，不能同时启用旧 `PlayerController.Update` 和新的外部移动驱动。

### 5.2 配置层次

| 层次 | 内容 | 生命周期 |
|---|---|---|
| Player 基础定义 | Prefab、基础速度、交互范围、基础能力及外观默认值 | 项目资产，只读 |
| 场景 Player 配置 | 本场景默认覆盖值、允许能力、镜头/HUD 方案 | 场景配置，只读 |
| 单个出生项 | ActorId、出生点、该角色需要的少量差异 | 当前场景角色定义，只读 |
| 运行时状态 | 最终实例参数、临时效果、能力执行状态 | 每名 Player 独立，默认随场景结束清理 |

配置覆盖顺序固定为“基础定义 → 场景覆盖 → 单个出生项覆盖”。没有填写覆盖项就继承，而不是被默认 0/false 意外覆盖。能力默认继承，仅在明确声明的启用/禁用/追加项中改变；重复能力键、重复角色身份由校验报出。

运行时效果在解析后的基础属性上计算，**不是回写上面的配置资产**。每个 Player 有自己的效果容器，不因共享一个 ScriptableObject 而互相改变速度或能力状态。

### 5.3 能力与特性的扩展方法

- **能力**是可执行行为，例如跳跃、冲刺、搬运；**特性/属性**是描述或参数，例如速度、交互范围、能否使用某类工具；**临时效果**具有来源与期限，例如减速。
- 新能力实现一个小型能力组件/接口，由 Player Prefab 或明确的能力安装配置提供。场景只选择实际存在的能力，不能仅写一个“飞行”字符串就假定有对应实现。
- 基础能力在组合时注册；场景覆盖在开始接收输入前解析。能力启用、禁用、角色失去控制、场景结束都需要有清理出口。
- 能力通过意图/命令向 Motor 请求移动，不从外部脚本直接改 Transform。第一版约定单一移动执行者：普通移动为基线，冲刺等独占移动请求有明确的优先级和结束时机。
- 需要全新移动模式时可以扩展 Motor 的移动策略契约，这属于合理的相关修改；不能承诺飞行、攀爬等任意能力完全无需调整移动系统。
- 第一版用一个独立的冲刺能力验证扩展：两个场景共享同一基础 Player，一个开启、一个关闭。其实现与场景配置都不依赖庆典代码。

临时效果至少带 `SourceId`、效果类型、数值、到期时间和叠加策略。相同来源的刷新、不同来源是否叠加及属性下限必须明确。例如当前偷吃可以用“叠加层数、刷新同一到期时间、到期整体移除”的策略描述；不应硬编码成所有 Demo 的减速方式。

### 5.4 自动放入场景的规则

只有带 `DemoSceneRoot` 的场景启用工具运行时。不能在项目每个场景启动时全局注入 Player，否则菜单场景、展示场景和旧作品都会受到影响。

每个场景选择一种互斥方式：

- **SpawnFromProfile**：运行时按出生项从 Prefab 生成 Player。适合快速新建 Demo。
- **UseScenePlaced**：接管已经摆在场景里的 Player，验证身份和引用，不额外生成副本。
- **None**：不创建或接管 Player，保留展示或纯交互演示场景的可能性。

生成数量由配置决定，不固定三人。出生点包含位置与朝向；Prefab 必须被放入当前拥有它的场景/运行根，不能因另一个活动场景而生成到错误位置。

启动顺序：

1. 校验场景唯一运行根、目标/角色身份、出生点和必要资源；无效配置给出清楚的作者提示，不静默生成在世界原点。
2. 创建场景上下文和时钟，注册交互物及业务适配器。
3. 生成或接管 Player，注入解析后的配置、明确的出生姿态和场景服务。
4. 初始化能力与运行时效果，完成镜头、Scene UI、可选 HUD 的绑定。
5. 选择默认主控，开放唯一输入入口，宣布场景就绪。

`Awake` 只缓存本地组件引用，不执行依赖尚未接线服务的动作，也不靠手动再次调用 `Awake` 完成重置。出生姿态由初始化显式传入；重置角色应回到指定 SpawnPoint，而非生成过程中偶然缓存的位置。

销毁顺序：停止输入 → 结束本场景运行实例/能力 → 解除 UI、事件和镜头绑定 → 移除注册 → 清理本运行根生成的对象。接管的编辑场景对象不通过“清理生成物”逻辑误删；场景卸载仍由 Unity 管理其销毁。

重复初始化、重新启用运行根、再次进入 Play 必须幂等，不再生成一批角色或增加一轮订阅。第一版禁止重复的已启用运行根；允许编辑多个场景，但不支持多个根争抢同一套输入/相机。跨场景保留 Player 和叠加场景控制权仲裁留待明确需求，不默认使用 `DontDestroyOnLoad`。

## 6. Scene UI、主 HUD 与反馈

### 6.1 Scene UI 随对象配置

每个对象可声明自己的 UI Prefab、跟随锚点、数据绑定和显示条件。例如 `Focused`、`InRange`、`Running`、`FeedbackActive`；多个条件如何组合需显式配置，不在 HUD 中按对象名称逐个特判。

第一版先实现一种渲染适配器。可以是世界空间 UI，也可以是投影到屏幕的 UI；对象拥有语义和配置，公共渲染器负责绘制。未来换渲染方式不改行为。UI 被隐藏或暂时禁用时，只减少显示，不注销业务对象、不重置进度。

新绑定时立即同步当前状态，再接收增量事件；对象被销毁时清理提示与飘字。局部 UI 只读本对象与当前观察角色的数据，不持有整个场景控制器并任意操作它。

### 6.2 HUD 按 Demo 选择

场景配置可以选择不使用 HUD，或者挂主控身份、快捷提示、最近日志等独立面板。回顾窗口属于需要此业务的 Demo，不强迫所有工具场景都有奖杯和日志。

输入占用通过通用服务按窗口申请/释放。普通提示与进度不占输入；模态窗口可以占移动/交互通道，但不会自动暂停对象运行。窗口销毁必须释放自己的占用，不影响其他申请者。

## 7. 快速构建场景的工具边界

### 7.1 最小编辑流程

“创建 Demo 场景”入口选择模板和新路径，生成：运行根、简单地面与边界、出生点、可选镜头和 HUD 绑定。第一版提供广场/室内平地等少量模板即可，不制作自动城市生成器。

“添加交互物”优先采用 Prefab 拖放和 Inspector 配置。可以增加一个轻量菜单创建带必要组件的空物体，但不先做专用节点编辑器或大型资源浏览器。

模板解决空间起点，Prefab 解决可复用配置，行为脚本解决交互规则。不能把所有交互类型和摆放位置再次写死在一个 `CreateEverything` 生成函数里。

### 7.2 编辑安全与校验

- 新建默认不覆盖已有场景、Prefab 和用户资源，也不自动更改所有 Demo 的构建顺序或项目级设置。
- 生成物带明确归属；“重新生成”仅针对显式选中的生成区域，并提示会替换的内容。用户布局区域不受影响。
- 复制交互物需给场景实例分配不同 TargetId；身份不能只取物体名称，Prefab 的所有实例也不能共享同一个场景身份。
- 校验覆盖：缺失行为、引用为空、重复 ID、缺少出生点、能力未安装、多个输入入口和重复运行根。可以给出修复入口，但不能自动重写用户未知用途的资源。
- 模型层级与名字不参与规则判断；锚点、Renderer、Animator 等通过显式引用配置。
- 模板与行为配置采用只读资产；对象运行状态在场景实例中建立。重置运行状态与重建编辑场景是两项不同操作。

## 8. 开发顺序与任务颗粒度

本表是待办队列，不是本轮开发授权。后续每次只派发一个编号给一名 Luna xhigh 子 agent，完成针对性验证、提交与推送后停止。需要超出一行边界时先拆小；不同时启动整阶段。

每项下发时只给相关契约、文件范围、一个完成目标和直接验收方式。当前作品 W 系列不必全部完成才能启动工具；若对应边界已在 W 系列完成，复用一次实现，不在两处维护两份同功能代码。

## 9. 最小复用证明与验收标准

推荐用两个轻量样例验证，不扩大成两款完整游戏：

- 样例 A：开关灯与切换装饰，单角色，普通移动，最小局部提示。
- 样例 B：协作维修台，两名可切换角色，一个按场景启用冲刺，带临时速度效果和可选日志。

验收不是“所有组件都有一个类”，而是完成以下实际操作：

1. 新建场景，选已有 Player 配置，运行后出现在指定出生点；不复制移动脚本。
2. 拖入同一个交互 Prefab 的两个实例，分别执行且状态不串；改变其中一个的时长和 UI，不改另一个。
3. 新增一种业务行为，只增加行为实现与对象配置，不修改全局类型枚举、PlayerMotor 或其他交互物。
4. 两人参与共享计时，切换角色和隐藏 UI 不影响实际进度；共享完成只发生一次。
5. 换一种模型或取消主 HUD，只调整绑定与配置，玩法仍可操作。
6. 两场景共享基础 Player，但能力与参数不同；运行时效果不回写配置资产，重新进入场景没有上次残留。
7. 场景卸载、对象删除、重置和重复初始化均没有双输入、重复生成或失效引用。
8. 如果接入庆典，会话仍是庆典规则唯一所有者；不把称号、蛋糕六点和三人奖杯写进通用工具。

每个小任务只运行与其风险相关的验证。计时、身份、效果和生命周期适合行为测试；Prefab 接线、局部 UI 和出生位置必须有 Unity 实际操作证据。静态编译和源码检查不替代可体验结果。

## 10. 后续扩展的取舍

未来可以增加其他镜头、按住/可中断交互、搬运能力、跨场景角色保留和联网适配，但应以一个真实 Demo 的需求触发，每次新增一个清楚的扩展点。

先用 T1 证明最小工作流，再根据制作新 Demo 时真正重复的工作推进 T2～T4。没有复用压力的部分保留简单实现；不要求把“所有未来可能的玩法”提前做成配置系统。
