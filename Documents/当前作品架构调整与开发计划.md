## 1. 结论与计划调整

当前作品已经有领取、购买、捐献、协作加工、蛋糕装饰、偷吃、庆典、奖杯和回顾的实现，用户也已实际体验并确认基本功能成立。后续工作的目的应当改为：**保持现有体验，收紧状态、交互、表现和场景装配之间的边界，让后续修改落在与需求相关的模块内。**

不再把旧 B～G 清单当作一组需要重新开发的功能。旧清单保留为规则与回归检查的索引；确实发现缺陷时，再开有明确现象和结束条件的小任务。也不因为旧表有待办项，就自动继续逐项补测试、拆文件或重写实现。

## 3. 目标架构：只建立必要的边界

### 3.1 数据流与依赖方向

1. 场景装配入口建立会话、角色/目标注册表、输入路由、镜头与表现组件之间的引用。
2. 输入路由把玩家指令交给当前角色；目标选择只处理候选、距离、朝向和稳定排序。
3. 交互应用层按角色和目标提交命令，调用 `DemoSession`。资格规则由规则侧给出，选择器不认识“奖杯”“筷子”。
4. 会话完成状态变化，保存业务记录，产生不可由表现修改的结果/事件。
5. World 表现、Scene UI、HUD、回顾界面分别读取所需状态，或响应相关事件。

依赖必须朝向玩法状态与小型数据契约。玩法核心不依赖 Canvas、动画、粒子、模型层级或具体 HUD；任何表现组件都不能写入角色统计、工位进度、奖杯状态和历史。

`DemoRuntime` 可以继续作为装配与调度入口。无需立即引入依赖注入框架、全局消息总线，也不要求每个类都有接口。只有确实需要替换的边界，例如输入占用、状态读取、表现出口，才建立小接口。

### 3.2 责任与状态归属

以下名称是拟议责任名称，不表示已经存在同名类；允许在小项目内用少量组件实现。

| 模块 | 拥有什么 | 对外提供什么 | 不负责什么 |
|---|---|---|---|
| 活动会话 `DemoSession` | 唯一玩法状态、活动时间、加工批次、效果期限、参与资格、结算与完整记录 | 命令、只读状态、业务事件 | 输入、相机、界面、模型 |
| 交互应用层 | 一次交互从解析到执行的调用顺序 | 当前动作描述、执行结果 | 保存另一份库存或规则状态 |
| 输入路由与输入占用 | 当前主控、输入分发、各输入通道的占用 | 移动/交互/切换指令 | 读取具体弹窗组件、暂停工位时间 |
| 角色表现与移动 | Transform、碰撞移动、选中表现、头顶锚点 | 移动执行、位置与锚点 | 称号、日志、协作进度 |
| 目标选择与注册 | 场景内候选目标、稳定 ID、选择结果 | 当前目标和焦点变化 | 奖杯归属等具体业务规则 |
| 对象表现 | 本对象的模型引用和显示状态 | 工具动作、蛋糕样式、奖杯显示 | 更新工位、蛋糕或奖杯的业务状态 |
| 对象 Scene UI | 本对象的提示、进度、反馈锚点及显示条件 | 局部界面 | 建立第二套交互入口或进度计时 |
| 活动表现协调器 | 业务结果如何映射为展示流程 | 调用当前结算/回顾展示方式 | 决定称号、发奖次数和物品增减 |
| HUD 与日志/回顾视图 | 窗口、样式、滚动位置、最近显示范围 | 消费完整记录的只读窗口 | 因窗口被清空而删除活动历史 |
| 场景装配与生成工具 | 引用接线、生成物归属与编辑校验 | 明确的场景配置 | 在运行时重建手工场景、拥有玩法状态 |

### 3.3 时间、查询与事件约束

- 运行时只有一个活动时间来源；每帧先推进会话，再读取状态和处理本帧指令。命令入口必须明确使用已经推进到的时间。
- `Resolve`、`GetSpeed`、历史查询等不能改变状态或发事件。带时间参数的旧接口只作为兼容转发入口，不能再自行推进同一工位的另一套时间。
- 工位拥有自己的共享批次；切换控制角色、离开位置、隐藏 UI 均不改变参与关系。不得把进度放到主控 Player 或进度条组件上。
- 状态只读不只是 `IReadOnlyList` 包住一个列表；列表内的事件、参与者数组等也不能向视图暴露可写的内部引用。已有 `Clone` 可复用，不必立刻引入复杂不可变集合。
- 将事件标识、动作标识、对象/角色归属、数值变化与显示文案区分。先兼容旧字段，逐类迁移，不一次替换全部日志协议。禁止让新的业务逻辑解析中文文本。
- 业务提交成功后，某个 UI/特效回调失败不能阻止其他记录和表现分发。订阅在场景作用域内管理；业务状态不得在表现回调里再次提交。
- 晚启用的视图先读取当前状态，再监听变化；不能只能靠“刚才发过的一次事件”恢复画面。
- 保留完整个人活动回顾；最近日志可以限长，完整活动记录不能被显示窗口裁掉。本轮不新增跨启动存档。

### 3.4 表现与交互解耦

交互结果描述“已结算”“请求查看某人的活动记录”等语义；具体开哪个界面，由表现协调器决定。拆分时继续使用现有展示方式，不借架构任务改变庆典节奏或界面显隐。

Scene UI 在职责上属于交互物：物体提供数据源、锚点与显示配置。渲染可以采用世界空间 Canvas，也可以由公共渲染器投影到屏幕；两者都不应让一个主 HUD 拥有所有交互物的业务逻辑。

窗口申请移动/交互等通道的输入占用，关闭、被销毁或重置时释放。占用应能区分申请者，避免一个窗口关闭就解除另一个窗口的占用。沿用当前“界面打开时活动仍推进”的行为；角色切换、Esc、重置的现行规则在迁移时保持。

`TargetView` 最终保留身份、交互半径、焦点和锚点等共同信息。工位进度、蛋糕样式、奖杯显隐交给各自表现组件，以序列化引用绑定模型。更换模型不应要求它含有固定名称的 `Tool` 或 `CreamSurface` 子节点。

### 3.5 装配、重置与生命周期

- 运行时依赖优先由场景入口显式提供；保留必要兼容查找时，限定在当前场景/生成根内。不能在多个场景中随意取第一个 HUD 或相机。
- 重置顺序统一：暂停接收新指令 → 解除输入占用/停止旧表现任务 → 重置会话 → 复位角色、目标焦点和镜头 → 重新同步视图 → 恢复输入。
- 表现的延迟任务携带活动身份；重置后旧活动的回调不得修改新活动的画面。销毁、禁用、重复初始化时都需要解除订阅或保持幂等。
- 生成器的新建操作使用新路径；重建现有生成根必须显示会替换的范围，并处理未保存场景。手工区域、已有 Player 配置及用户资源不得被隐式覆盖。
- 暂不为当前作品新增跨场景常驻对象，也不把工具工程的 Player 自动生成方案强行接入当前三角色场景。

## 4. 分阶段小任务顺序

**后续每次默认只执行一行，使用一名 Luna xhigh 子 agent；主 agent 做针对性审查与验收。** 每行是责任边界，不是必须一次完成的工作量；预计需要同时改动多个无关模块时，再拆成 `.1`、`.2`，不能顺便推进下一行。表内所有任务目前均为未执行。

派发内容必须包含：这一行的目标、允许修改范围、保留行为、直接依赖、验收与停止点。完成后按已有授权提交并推送阶段成果，再停下。

### 阶段 W1：状态和表现之间有可靠边界

这一阶段优先级最高，直接降低后续需求造成规则回归的风险。W01 是建议的下一项；不自动派发。

| 编号 | 本次只做什么 | 主要修改范围与依赖 | 可检查的结束条件 |
|---|---|---|---|
| W01 | 将查询中的到期处理移回时间推进路径 | Core 的 `GetSpeed`、`Resolve`、到期处理及相关验证 | 同一时刻反复查提示/速度，不增加事件、不改变状态；推进时间后正确到期 |
| W02 | 收拢带时间参数的兼容入口 | Core 时间入口及直接调用点；依赖 W01 | 所有入口使用同一时间，重复推进不重复完成批次、不重复发到期事件 |
| W03 | 角色状态建立只读访问边界 | Core 角色读取接口及直接消费者 | 表现不能改参与资格、减速或奖杯；移动和反馈行为保持 |
| W04 | 工位与蛋糕建立只读访问边界 | Core 工位/蛋糕查询及直接消费者 | 外部不能改参与者集合、进度、蛋糕数组；切人和协作不变 |
| W05 | 完整历史与事件分发隔离内部可变引用 | Core 记录出口、订阅适配及相关验证 | 视图拿到的数据不能污染历史；表现异常不改变业务结果或截断后续颁奖记录 |
| W06 | 从执行结果分离具体开窗决策 | Core 结果、Runtime 分派、一个表现协调组件；依赖 W05 | 默认仍以当前方式展示；替换展示接收者不需要修改结算、发奖和回顾规则 |
| W07 | 输入限制不再读取具体 HUD | Runtime、输入占用组件、现有弹窗适配；依赖 W06 | 窗口正常占用/释放，销毁不残留锁；无 HUD 时仍能交互，活动时间不随弹窗停止 |

阶段停止条件：规则写入路径清楚，查询只读，结果展示可替换，输入不依赖具体界面。达到这里就可以停下；不要求为了继续美化先完成后续全部拆分。

## 5. 验收以行为和修改范围为准

### 5.1 必须保持的体验契约

- 三角色身份、位置和行为归属独立；1/2/3 只切换主控，镜头保持角度并平滑移向角色。
- 单人加工需要 10 秒；多人按实际参与时间加速，同一人不能重复占多个协作名额。切换或离开不中断；共享产出不按人数重复计算。
- 无库存与余额门槛；日志只记录动作产生的增减。没有先加工也可装饰蛋糕。
- 有有效筷子时水果/鸡蛋堆自动变为偷吃，不能捐献；切果、打发、装饰不受影响，不增加手动模式切换。
- 偷吃减速按现行规则累积，速度最低 0；每次刷新 10 秒到期时间，到期移除全部偷吃减速。
- 蛋糕保持三个果切挂点和三个奶油区域。称号按参与资格获得，不恢复“做得最多”排名。
- 任意玩家可触发庆典；同一活动不会重复颁奖，三人各获奖杯；回家放置后可查看本人完整活动记录并关闭。

“无库存门槛”不意味着没有目标归属、筷子资格或奖杯阶段规则。架构调整不得把这些有意存在的资格判断一起取消。

### 5.2 应证明的变化隔离

| 验证操作 | 预期修改或影响范围 |
|---|---|
| 更换一种对象模型及锚点 | 对象表现/Prefab 绑定，不改领取、协作和结算 |
| 替换或不挂载一种 HUD | 装配与表现配置，输入和活动状态仍成立 |
| 修改提示文案 | 格式化/显示配置，不改变统计和行为归属 |
| 多次读取进度与历史 | 只读；不加速加工、不增加记录 |
| 重置时存在未结束的显示任务 | 旧任务被清理或拒收，不影响新活动 |

验证使用已有规则检查，加上本次变更对应的行为检查与必要的 Unity 操作检查。不要为一个纯显示拆分重跑所有无关环境流程，也不要用匹配源码字符串、增加断言数量替代运行行为证据。本轮是文档工作，不新增或运行这些测试。

## 6. 开发边界与投入控制

- 不实现完整 Demo 工具、不搭行为树/节点编辑器、不迁移整个旧 `_Project` 系统。
- 不新增真实联网、持久化存档、真实库存经济、昼夜天气模拟或自动路人 AI。这些并非本次架构稳定所必需。
- 保留当前可体验场景作为回归基准；逐个边界替换，避免新旧实现同时接收同一次 F 或同时推进时间。
- 一个优化如果自然只涉及一个视图，直接在该视图任务里完成即可；不能借“先完善架构”要求完成整张表。
- 一旦某项改造无法说明“为哪一种实际变化减少了哪些依赖”，暂不执行。
